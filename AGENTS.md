# Agent Instructions

## Commands

- Use Node.js 20+ and the pnpm version pinned in `package.json`. pnpm is the sole supported JavaScript package manager for this repository and any submodules. Install dependencies with `pnpm install`. The Dockerfile takes pnpm from its official image at the same pinned version.
- Run the development server with `pnpm dev`; production checks are `pnpm build` and `pnpm start`.
- Before handing off changes, run `pnpm lint` and `pnpm typecheck`; there is no configured test runner. For UI copy/localization changes, also run `pnpm i18n:check` (translation coverage, placeholder parity and locale/fallback isolation).
- Local MongoDB must be a replica set (for example `mongod --replSet rs0`, then `rs.initiate()` in `mongosh`) because entity writes use transactions.

## Structure

- **Site i18n**: `lib/i18n/index.ts` owns `zh-CN` (default) and `en-US`, using Chinese source strings as keys/fallback and `lib/i18n/en-US.json` as the English dictionary. Interpolate dynamic values with `t("…{0}…", { "0": value })`; never construct a translated key from user data. `lib/i18n/server.ts` reads the allowlisted `messenger_locale` cookie with request-scoped React cache; Server Components await `getTranslator()`, while Client Components call `useTranslator()` from the root `LocaleProvider`. Never use a mutable process-global locale, DOM text replacement, or translate user-authored names/prompts/messages. Root HTML lang and generated page metadata use the request locale. `LanguageSwitcher` uses shadcn DropdownMenu radio items at public/auth/console/chat entry points, saves the cookie for one year, and refreshes RSCs without changing URLs or resetting mounted client drafts. Dates and token abbreviations receive `t.locale`; pricing currency stays CNY. Single-use email verification must not re-run on language changes, and remote relay connections/pending calls must survive them. Keep new UI strings in the dictionary and run `pnpm i18n:check`.

- This is a single Next.js App Router application, not a workspace despite the `pnpm-workspace.yaml` file. Pages are under `app/` (official website at `app/page.tsx`, auth pages under `app/login|register/`, shared web console under `app/console/`, independent chat under `app/messenger/`); API route handlers are under `app/api/` and `app/v1/`.
- The web frontend is built with **Tailwind CSS v4 + shadcn/ui** (init with the `radix` base and the `nova` preset — Lucide icons + Geist fonts via the `geist` package). Pre-built shadcn components live in `components/ui/` and are generated by the shadcn CLI (`pnpm dlx shadcn@latest add <component>`); do not hand-roll styling that a shadcn component already provides. Dark/light follows system preference via a media-query token block in `app/globals.css` (no `.dark` class). Console layout uses the shadcn `Sidebar` in `components/console/console-shell.tsx` (client) wrapping RSC pages; action feedback uses `sonner` toasts mounted in the root layout.
- **Scrolling**: Every scrollable Web UI region MUST use the shadcn `ScrollArea` from `components/ui/scroll-area.tsx`. This applies to both axes, including dialogs, menus and submenus, sidebars, lists, and tables. Add the shadcn `ScrollBar` for horizontal scrolling. The `ScrollArea` viewport must own scrolling. Override native overflow on surrounding component wrappers when necessary to prevent competing scrollbars.
- `lib/storage.ts` is the persistence boundary for users, agents, conversations, providers, incremental sync watermarks, tombstones, plans, card keys, redemptions, the AI model catalog, upstreams, usage logs, and overview aggregations (`lib/sessions.ts` owns the `user_sessions` records behind the login cookie). `lib/mongo.ts` also initializes indexes and runs the one-time admin-bootstrap migration on first database access.
- Effective rate resolution is single-sourced in `lib/model-rates.ts`: `实际倍率 = tokenTypeCard ÷ baseCard × modelRate × providerRate`, per token leg. Four legs are priced (`input` / `cacheRead` / `cacheWrite` / `output`); `tokenTypeCard` resolves per model through one chain: non-empty custom values, then `upstreams.modelPrices[modelId]` (the upstream's own `/v1/models` rates, refreshed by probing), then pi-catalog (`lib/pi-catalog.ts`); empty custom fields inherit that chain; explicit 0 is free. The editor no longer writes an override switch; legacy `override=false` suppresses dormant rate fields until edited. A leg the upstream does not return (absent or `0`) falls back per-leg to pi-catalog, default 1x; `0` = free is only reachable via an explicit custom override (pi-catalog's own `0` is a real free rate). Long-context tiers and peak/off-peak schedules are structural and taken from ONE source whole (custom → upstream → pi-catalog), never merged leg-by-leg, or a threshold would pair with another source's price. `modelRate` is `upstreams.modelMeta[modelId].multiplier` (per-model overall multiplier); `providerRate` is `upstreams.multiplier`. The 1x base model lives in the `model_rate_settings` singleton (`baseModelId`); stored rates never change when the base switches — the base is a read-time divisor applied per leg, so relative prices stay constant and the change is reversible (the base model itself is exactly 1x on every leg, including a free `cacheWrite` of 0). `/v1` billing (`lib/ai-relay.ts`), the model plaza (`lib/model-plaza.ts`), `/v1/models`, and the console all call `resolveModelRates`. `lib/pricing.ts` owns the pricing primitives shared by all of them: tier selection (exclusive by default, `inputThresholdInclusive` opt-in), UTC peak windows (Sunday = 0, start inclusive / end exclusive), and `effectiveRates(card, { promptTokens, atMs })`, which picks the tier then applies the peak/off-peak multiplier. Billing resolves with the request's REAL usage (`startedAt` + the upstream-reported prompt total) so a long request spanning a peak boundary is priced by its start; console/plaza views pass no usage and get the base tier at peak price for comparison. pi-catalog (`https://pi.dev/api/models`, cost normalized against `deepseek/deepseek-flash`'s output price = 1.0, `cacheWrite` falling back to `cacheRead` and `cacheRead` to the input price) reads the provider→model JSON map (providers validated independently), keeps provider-qualified keys authoritative over colliding aggregator model IDs and prefers canonical providers for bare aliases, maps `longContext` to internal `tiers` (including inclusive thresholds), and carries `cacheWrite` and `timeBased`; it is cached in-process for 24h AND persisted to the `model_metadata` singleton (`_id = "pi_catalog"`) after every successful fetch: a cold instance that cannot reach pi.dev falls back to that snapshot instead of collapsing every model to 1x. The old models.dev pricing probe was removed — models.dev remains the Android/Desktop context-window source. After catalog loading succeeds, models with neither a catalog match nor explicit metadata/rate/multiplier/schedule configuration show an 未配置 badge; drafts update this status immediately, and an unresolved catalog target alone does not count as manual configuration. The console's per-upstream model table is deliberately minimal (model ID / effective display name / current effective rates / actions) and carries NO inline rate inputs: every per-model setting (capabilities, four optional legs, model multiplier, tiers, peak windows) lives in the `ModelEditor` dialog opened by 编辑, and 停用/启用 writes `disabledModels` vs `models` directly (probing auto-enables what it finds). An untouched editor must not fossilize inherited tiers/schedules into custom values — only drafts the user actually edited are written back.
- Versioned entity mutations must remain in the MongoDB transaction that increments the user `syncVersion` and stamps the entity `version`; sync reads first capture the waterline and bound collection queries to it. The legacy merged `GET /api/sync` (no `collection=`) is bounded to `SYNC_MAX_LIMIT` per collection and reports `truncated` plus a delivered-only `latestVersion` — never return the user's full `syncVersion` for a truncated page, or the skipped rows are never pulled again. All four synced collections (`agents`, `conversations`, `providers`, `projects`) need a `{ userId: 1, version: 1 }` index. Upstream model ids are the reverse: `upstreams.models` is the single source of truth for what an upstream serves (`listUpstreamsForModel`'s query, the model plaza, `/v1/models`, and relay failover all read only it) — a per-model stop keeps the id in `disabledModels` while removing it from `models`, and deleting a model drops it from `models`, `disabledModels`, `modelMeta`, and `modelPrices` alike.
- Messages are embedded in conversations and models are embedded in providers. Deletes are soft deletes so tombstones remain available to `GET /api/sync?since=N`.
- Multimodal images are NOT stored as blobs: each message may carry a `partsJson` string (validated by `messageSchema`, stored verbatim, returned untouched by sync). Image parts embed the full base64 `data:` URI plus the sender's device-local path; clients rebuild missing local files from the `dataUri` after a pull. Do not strip, re-encode, or reorder `partsJson` server-side — the mobile client relies on byte-identical round-trips.
- Avatar objects are stored in a private S3-compatible bucket behind `lib/blob-store.ts`. `lib/avatars.ts` handles prefix snapshots/replacement/rollback, authenticated avatar GET routes stream content through ETag-conditional responses, and a recorded `avatarUrl` whose object is gone is a 404 (`fetchAvatarWithConditional` returns null), not a 500. `lib/avatar-locks.ts` serializes changes through MongoDB. Every avatar mutation path — user, agent, and market agent — MUST run inside `withAvatarLock` and thread the `verify` callback through snapshot/upload/revert/delete; unpublishing a market agent deletes its object. New modules must go through the `BlobStore` interface, never the SDK directly.
- All users (including admins) share the `messenger_session` JWT cookie from `lib/auth.ts`. `requireUserSession()` accepts any valid session; `requireAdminUser()` additionally verifies the database `role === "admin"` — every admin-only route and page must go through it. There is no separate admin cookie and no `ADMIN_PASSWORD` env.
- **Sessions are server-side** (`lib/sessions.ts`, `user_sessions` collection) and do double duty: (a) the JWT is only a credential and must carry `sid`; `requireUserSession()` rejects a token whose `sid` has no row, so logout / password change / the 30-day expiry take effect immediately (a plain JWT cannot be revoked); (b) each row is a **sync-progress ledger** — `syncCursor` records the `syncVersion` that session has fully applied. Signing in mints one row per device (several coexist, none displaces another); sign-out / password change / expiry DELETE the row (sessions carry no tombstones — a missing row is an invalid session) with the `expiresAt` TTL index as the backstop. `DELETE /api/auth/account` deletes the user's sessions. Tokens issued before this change have no `sid` and are rejected, so every client re-logs in once after upgrading.
- **Entity tombstones are purged from the session ledger** (`purgeSettledTombstones`): soft-deleted agents/conversations/providers/projects must stay until every client has pulled them, and nothing used to record that, so they accumulated forever. Now the account's OLDEST live session's `syncCursor` C is a safe lower bound — delete every tombstone with `version <= C`, since delta sync only ever asks for `version > since`. It runs when a session's cursor advances and at login. Two conservative rules: no live session ⇒ purge nothing (a re-logged-in device returns with its own local cursor and still needs them), and `syncCursor == 0` ⇒ purge nothing (that session's local state is unknown). Clients report the cursor through `GET /api/sync?ack=N`, which MUST be the version they have DURABLY applied — never the `since` of a post-push pull (that version is not applied yet), which is why the engine sends its stored cursor rather than echoing `since` and sends nothing on a full pull (`since=0`, local state being rebuilt); requests without `ack` simply do not advance the ledger. The purge horizon is the 30-day session lifetime: a client offline longer than that must re-login, and login always rebuilds the local store in full instead of resuming from a stale cursor.
- Runtime logging is file-backed, never stored in MongoDB. `instrumentation.ts` awaits Node-only capture installation before serving requests; `instrumentation-node.ts` delegates to `lib/runtime-logs.ts` and records framework errors with request metadata. Capture wraps `process.stdout.write` / `process.stderr.write` once per process (global state survives Next bundles/HMR), preserving terminal output, callbacks and backpressure; each write becomes a JSONL record (`info` for stdout, `error` for stderr). Business events use `createLogger(source)` / `recordRuntimeLog`, emitting structured JSON to stdout (`info`) or stderr (`warn`/`error`) and the file sink exactly once, retaining source, level and details. Files are `RUNTIME_LOG_DIR/runtime-YYYY-MM-DD.jsonl` (UTC, default `./logs`); serialized appends create the directory and remove daily files older than 30 days on the first write each UTC day. File/serialization failures report via the raw stderr writer without recursion. `listRuntimeLogs` streams file snapshots for time/level/source filtering, count and descending `(createdAt, _id)` pagination; missing directories are empty, malformed records are skipped, other filesystem errors surface. The admin page/API read only these files; no legacy collection fallback or automatic database deletion. Keep this deployment single-instance with a writable persistent log directory (Compose mounts `runtime-logs` at `/app/logs`). Do not log successful per-request events already covered by usage/audit records. The page table shows time / level / source / summary; request metadata and details live in a per-row dialog, with absent fields and empty context sections hidden. Format timestamps and details in the RSC before passing them to client components.
- The first-admin invariant is enforced in two places: the registration transaction (unique `system_bootstrap` marker makes concurrent first registrations produce exactly one admin, retried as a plain user on marker conflict) and the idempotent `ensureAdminBootstrap` migration in `lib/mongo.ts` (promotes the earliest-registered user of pre-SaaS deployments).
- Billing and the AI relay are split across `lib/apikeys.ts` (key/card-code generation), `lib/quota.ts` (quota state, token estimation, `cost = max(1, ceil((promptTokens − cachedTokens − cacheWriteTokens) × inputRate + cachedTokens × cacheReadRate + cacheWriteTokens × cacheWriteRate + completionTokens × outputRate))`; all four rates zero → free; `usage_logs` stores UNCACHED input in `promptTokens`, cache reads in `cachedTokens`, cache writes in `cacheWriteTokens`, and the applied `longContextThreshold` / `timeMultiplier` for reconciliation), `lib/ai-proxy.ts` (Bearer-key auth + OpenAI error bodies), `lib/ai-formats.ts` (the four wire formats — OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini Interactions — decoded into one IR and re-encoded, requests and SSE both ways; dependency-free so it can be exercised outside Next; the decoders own tool-call identity: consecutive sibling `function_call`/`function_result` items are one assistant turn with multiple calls, and a per-request ledger guarantees every call and its result resolve to the same id — synthetic when absent, unmatched results dropped, unanswered calls closed with an explicit error result), `lib/ai-relay.ts` + the four `/v1/*` routes (upstream failover by `priority`, upstream format chosen per upstream `apiFormat`; `auto` = follow the client's protocol AND relay it verbatim — the client's request bytes and the upstream's response/SSE bytes are forwarded untouched with no IR round trip, only a side-channel `data:` sniff for `usage`, so nothing is added or rewritten; configured formats still go through stream conversion with usage sniffing; post-completion quota settlement; every attempt — connect failure, 5xx, unparseable body, or a retryable 4xx — is recorded through `createLogger("relay")` and fails over, only 413/415 short-circuit, and an exhausted pool returns 502 naming each attempt). There is NO global model catalog: `/v1/models` serves the union of enabled upstreams' models, and per-model metadata resolves per model — non-empty fields in `modelMeta[modelId]` use that entry's custom values (including optional `tiers` / `timeBased` / `cacheWriteRate`), empty fields use the upstream's `/v1/models` rates (`upstreams.modelPrices`, refreshed by `POST /api/admin/upstreams/{id}/probe` and carried back by the console form) falling back leg-by-leg to pi-catalog (`lib/pi-catalog.ts` — 24h cache + persisted snapshot, normalized against `deepseek/deepseek-flash`'s output price, `cacheWrite` falling back to `cacheRead` and `cacheRead` to the input price). The pricing probe against models.dev was removed. Android/Desktop derive context windows locally from models.dev `models.json`; Messenger Web reads pi.dev catalog capabilities through its authenticated metadata endpoint. Card codes embed a creation-time plan snapshot so plans can be edited or deleted without invalidating outstanding cards.
- User-center routes: `PUT /api/auth/profile` (nickname only — avatars stay on the shared `/api/avatars/user` multipart endpoint so web and app hit the same blob/lock/rollback path) and two-step e-mail rebinding (`POST /api/auth/change-email` then `/confirm`). Rebinding requires the current password (the address *is* the login identity), sends a 6-digit code to the NEW address, and the code is bound to `(userId, email, code)` because a 10^6 space is guessable; consuming it marks the new address verified and revokes every other `auth_tokens` row for the user. Sessions survive the change — they key off the user id, not the address.
- Account routes include authenticated password changes at `PUT /api/auth/password` and permanent account deletion at `DELETE /api/auth/account`; deletion removes the user's MongoDB entities, billing history, usage logs, `user_quotas` entitlements, pending `auth_tokens`, avatar locks, and avatar blobs before clearing the session cookie. The last admin cannot delete or demote themselves (`409`): `ensureAdminBootstrap` never re-promotes once the `system_bootstrap` marker exists, so the instance would lose every management entry point permanently.
- The self user view is single-sourced in `lib/user-view.ts` (`buildSelfUserView`): `GET /api/auth/me`, `POST /api/auth/login`, `POST /api/auth/register`, `PUT /api/auth/profile` and `POST /api/auth/change-email/confirm` all return it, including `quotaBalance`/`quotaExpiresAt`/`quotaEntitlements`, `aiApiKey`, `displayName`, and `emailVerifiedAt`. Clients treat the login response as the account snapshot, so any field missing there reads as "0 quota / no builtin AI provider" until the next refresh — never add a self-facing field to `/me` only.
- **E-mail flows** are optional at the deployment level and split across `lib/env.ts` (`smtpSettings()`, `null` when the SMTP host or credentials are missing), `lib/mail.ts` (nodemailer transport cached on `globalThis`, delivery failures logged and swallowed), `lib/auth-mail.ts` (`prepareVerificationEmail` / `preparePasswordResetEmail` / `prepareEmailChangeCode` issue the token and return a delivery thunk), and `lib/auth-tokens.ts` (`auth_tokens` collection). Tokens are single-use and stored as SHA-256 digests keyed by `_id`, so `findOneAndDelete` is the atomic consume; re-issuing deletes the user+purpose siblings, and a TTL index on `expiresAt` is only the backstop. Mail requires all of `SMTP_HOST`, `SMTP_USER`, and `SMTP_PASSWORD`. When enabled, `POST /api/auth/register/send-code` sends a 6-digit, 10-minute code with per-IP/per-email rate limits; registration requires `code`, consumes it inside the user/default-Agent transaction, and sets `emailVerifiedAt` immediately. Codes are mailbox/purpose-bound hashes in `auth_tokens`; each mailbox has one current code. Failed registrations roll back consumption. With mail disabled registration skips verification, and the web hides registration code controls, password recovery links/page, and the console verification banner. Existing unverified accounts retain the link flow; `POST /api/auth/verify-email/resend` re-sends for a signed-in user. `POST /api/auth/forgot-password` returns the same `{ success: true }` for unknown addresses (no account enumeration) and `503` when SMTP is unconfigured — never fake a send. `POST /api/auth/reset-password` consumes the token before hashing, revokes every session of the account plus all remaining tokens, and marks the mailbox verified. For existing accounts, verification remains informational and gates no signed-in feature; new registrations require the code only while SMTP is enabled.
- Agent Market entries live in a separate `market_agents` collection and contain only portable Agent snapshots (name, avatar, prompt, sampling parameters) — never providers, model bindings, or API keys. List/detail/publish/update/unpublish APIs require a Messenger session; market avatars stay private Blobs streamed through authenticated `/api/market/agents/{id}/avatar` routes. Imported Agents keep their market entry/version link but always clear model bindings; market updates require explicit user confirmation.
- Registration seeds the one required default Agent in the same transaction as user creation, so cloud data preserves the default-agent invariant. Default-role transfer is a claim: a `PUT` with `isDefault: true` demotes the incumbent inside the same `withVersionedWrite` transaction and stamps it with the new `version` (otherwise the demotion never enters the sync delta). A `PUT` that demotes the current default is deferred (the holder keeps the role) instead of rejected, because the client expresses a transfer as two PUTs in either order — rejecting either direction makes the role untransferable.

## Environment

- Copy `.env.example` to `.env.local`. `JWT_SECRET` and `MONGODB_URI` are required at runtime; `MONGODB_DB_NAME` defaults to `messenger`, and `APP_BASE_URL` defaults to `http://localhost:3000`.
- SMTP (optional): Any missing `SMTP_HOST`, `SMTP_USER` or `SMTP_PASSWORD` disables all outgoing mail (`mailEnabled()` is false) — registration still succeeds, accounts stay unverified, and `/forgot-password` answers `503`. When all three are set, `SMTP_PORT` (default `587`), `SMTP_SECURE` (default: implicit TLS only on 465), `SMTP_USER`/`SMTP_PASSWORD` (required), and `SMTP_FROM` (default: `Messenger Cloud <no-reply@APP_BASE_URL-hostname>`) configure the relay. nodemailer is a production `dependencies` entry and is pinned in `serverExternalPackages` in `next.config.ts`, so the Docker runner's prod-only `node_modules` must keep it resolvable.
- Avatar storage: `S3_BUCKET` is required; `S3_REGION` defaults to `us-east-1`; `S3_ENDPOINT` is optional. Supply `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` together or omit both to use the AWS credential chain. `S3_FORCE_PATH_STYLE=true` enables path-style addressing. Keep the bucket private and grant the server list/read/write/delete access.
- Keep secrets out of source control; `.env.*` is ignored except `.env.example`.
- Self-hosting: `Dockerfile` + `compose.yaml` package the server alone (MongoDB, S3-compatible storage and nginx are external). The runner stage gets production dependencies only, runs `next start` as the `node` user, and healthchecks `/api/plans`. Back up the bucket together with MongoDB. Any new runtime dependency must therefore be a `dependencies` entry, not `devDependencies`; keep `next.config.ts` free of options that break `next start` (for example `output: "standalone"`, which Next rejects at runtime).

## Conventions

- The upstream create/edit dialog and single/bulk model editor dialogs use a fixed viewport-relative height and keeps its header and Save/Cancel footer outside a themed shadcn `ScrollArea`. The single-model editor also gives wide tier tables a themed horizontal scrollbar, disables the generated table wrapper's native overflow, and keeps the outer dialog from scrolling. Only the form body scrolls, so the footer remains visible at the bottom even for long model lists; do not replace it with a native `overflow-y-auto` scrollbar.
- That `ScrollArea` owns BOTH axes: locally override the model table's generated `table-container` to `overflow-visible`, avoid `overflow-hidden` wrappers around it, and provide a themed horizontal `ScrollBar`. Keep form/grid columns constrained with `minmax(0,1fr)` so wide tables overflow into the shared viewport rather than creating nested scroll containers.
- Upstream models have a separate `checkedModels` selection for bulk actions; it never controls enabled `models`. The extra checkbox column has select-all/indeterminate state, and a persistent toolbar offers sequential tests (progress, per-row results, cancellation on stop/close), disable, confirmed delete, and bulk editing. Each bulk-edit field is opt-in (model multiplier, off-peak multiplier, UTC peak windows); preserve unchecked fields per model and validate the entire batch before merging drafts. Off-peak-only edits require existing peak windows; clearing windows alone restores inherited scheduling. Model multipliers and custom schedules are independent of individual rate fields, so always preserve explicit schedules and include disabled models when serializing metadata. Deleting models clears selection, drafts, stored metadata and quotes; deleting the last persisted quote must send `modelPrices: null` instead of omitting it.
- The upstream model table includes the union of discovered, enabled (`models`) and disabled IDs and stays sorted by ID regardless of enabled state. Enabling/disabling must keep the row mounted at the same position so the focused action and scroll viewport do not jump.
- The pi-catalog target picker is a searchable dropdown combobox built from shadcn `Popover` + `Command` (`cmdk` is a runtime dependency). Use `shouldFilter={false}` so the shared matching rank remains authoritative. Keep auto-match reset and progressive result display inside the dropdown; search supports keyboard selection through `CommandInput`/`CommandItem`.
- Per-upstream model metadata may set `catalogModelId` to an exact pi-catalog key independently of pricing. `catalogModelDefault` uses that target for the catalog fallback (rates, cache ratios, tiers and schedules); custom values and upstream quotes retain their priority. Missing/null restores automatic matching; a saved target absent from the current catalog stays selected and is treated as unavailable, never silently remapped. The model editor offers search across catalog IDs/providers, sorted by similarity to the current model (exact ID, equivalent normalized ID, then bigram similarity), with progressive result display and an explicit restore-auto action. Persist the selection alongside sparse rate/capability overrides.
- Default catalog matching is case-insensitive and unwraps BOTH the requested ID and pi-catalog keys via `matchModelDefault` in `lib/model-rates.ts`, shared by server rate/base resolution and the console. Try the full ID, remove a `-thinking|-high|-low|-medium` suffix, remove a `prefix(:|/)`, then both; nested provider prefixes are supported. Bedrock aliases also remove known vendor dot prefixes (optionally preceded by `us.|eu.|apac.|global.`) and `-vN[:N]` version wrappers. Dates and price variants such as `:free` remain significant. Exhaust direct catalog-key matches before unwrapping catalog keys; identical casing wins within a candidate, and catalog alias collisions use catalog order. Custom settings, upstream quotes, and relay routing still use the original full ID.
- Use the `@/*` path alias for imports from the repository root.
- API handlers validate request bodies and route IDs with the Zod schemas in `lib/validation.ts`, authenticate before accessing user data, and map storage failures through `lib/route-errors.ts`.
- Keep API routes that touch MongoDB or Blob on the Node runtime (`export const runtime = "nodejs"`).
- Segment config exports (`runtime`, `maxDuration`, `dynamic`, `revalidate`, `fetchCache`, `preferredRegion`, `dynamicParams`) MUST be written inline as a literal in the route/page file, at most wrapped in `satisfies`. Next parses them statically without resolving imports, so `export const maxDuration = RELAY_MAX_DURATION_SECONDS` aborts `next build` with `Unknown identifier … at "maxDuration"` (exit 1) — the `/v1` relay routes pin the literal with `120 satisfies typeof RELAY_MAX_DURATION_SECONDS` so `pnpm typecheck` catches drift instead.
- Outbound URLs (upstream `baseUrl`, probe/test targets) MUST pass `assertOutboundUrl()` from `lib/outbound-url.ts`. It validates URL syntax and requires HTTP(S), but permits internal DNS names, loopback, private and other IP ranges. Upstream management and probe/test routes remain admin-only; administrators own the destination configuration.
- Secret-guessing endpoints (login, register, card preview, redeem) MUST consume `consumeRateLimit()`/`enforceRateLimits()` from `lib/rate-limit.ts`; the counters live in MongoDB so they survive serverless horizontal scaling. Preview and redeem share one bucket so preview cannot be used as an unmetered card-code oracle.
- **Standalone web Messenger**: `/messenger` is the authenticated, full-viewport browser chat surface outside the console layout. It performs its own session/user checks and redirects unauthenticated visitors to `/login`. The left sidebar footer opens configuration management in a shadcn Dialog and links to the console/account. `/console/messenger` redirects to `/messenger`; `/console/manage` redirects to `/messenger?settings=1`. The chat header opens per-conversation settings (`conversation-settings.tsx`): the Provider → Model pair and nullable sampling/reasoning/tool overrides persist through the existing conversation PUT, update local state only after a successful save, and fall back to the effective Agent configuration (including follow-default flags). The composer’s bottom-left shadcn DropdownMenu opens a Provider submenu of enabled models and offers Follow Agent; it uses the same versioned PUT and only updates the active pair after success, without clearing the draft. Disable model changes during a turn and block sending while a quick selection is saving. It hydrates from the existing sync collections, persists conversations through `/api/conversations/:id`, and sends AI requests through the same-origin `/api/chat` proxy. `lib/conversation-model.ts` resolves the paired `providerId` / `overrideModelId`: explicit overrides never fall back to another Provider, and Follow Agent resolves the Agent model from enabled Providers. `/api/chat` keeps the built-in key server-side and delegates cloud calls to `relayCompletion`. For a custom `x-messenger-provider`, it looks up only the session user's saved, active Provider and validates enabled-model membership. BYOK uses its configured endpoint/protocol, the existing format converters and streaming bridge without cloud settlement, and never follows redirects or retries. Keep SSE error and missing-terminal handling visible to the chat error bubble and toast.
- **Provider model table and automatic defaults**: `components/messenger/provider-models-table.tsx` shows only display name/current rate for built-in Providers and display name/actions for custom Providers (selection checkboxes and status badges live inside the display-name column; model IDs remain searchable and available in tooltips/editors), with two-significant-digit rates, orange unconfigured tag, search, visible-only selection/bulk enable/disable/edit/delete and themed horizontal ScrollArea as upstream editing.
