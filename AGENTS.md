# Agent Instructions

## Commands

- Use Node.js 20+ and pnpm. Install dependencies with `pnpm install`.
- Run the development server with `pnpm dev`; production checks are `pnpm build` and `pnpm start`.
- Before handing off changes, run `pnpm lint` and `pnpm typecheck`; there is no configured test runner.
- Local MongoDB must be a replica set (for example `mongod --replSet rs0`, then `rs.initiate()` in `mongosh`) because entity writes use transactions.

## Structure

- This is a single Next.js App Router application, not a workspace despite the `pnpm-workspace.yaml` file. Pages are under `app/` (official website at `app/page.tsx`, auth pages under `app/login|register/`, shared web console under `app/console/`); API route handlers are under `app/api/` and `app/v1/`.
- The web frontend is built with **Tailwind CSS v4 + shadcn/ui** (init with the `radix` base and the `nova` preset — Lucide icons + Geist fonts via the `geist` package). Pre-built shadcn components live in `components/ui/` and are generated by the shadcn CLI (`pnpm dlx shadcn@latest add <component>`); do not hand-roll styling that a shadcn component already provides. Dark/light follows system preference via a media-query token block in `app/globals.css` (no `.dark` class). Console layout uses the shadcn `Sidebar` in `components/console/console-shell.tsx` (client) wrapping RSC pages; action feedback uses `sonner` toasts mounted in the root layout.
- `lib/storage.ts` is the persistence boundary for users, agents, conversations, providers, incremental sync watermarks, tombstones, plans, card keys, redemptions, the AI model catalog, upstreams, usage logs, and overview aggregations (`lib/sessions.ts` owns the `user_sessions` records behind the login cookie). `lib/mongo.ts` also initializes indexes and runs the one-time admin-bootstrap migration on first database access.
- Effective rate resolution is single-sourced in `lib/model-rates.ts`: `实际倍率 = tokenTypeRate ÷ baseRate × modelRate × providerRate`. `tokenTypeRate` is the stored input/cache/output rate (`override` on → custom values with models.dev fallback, off → models.dev, default 1x, 0 = free); `modelRate` is `upstreams.modelMeta[modelId].multiplier` (per-model overall multiplier, independent of the override switch); `providerRate` is `upstreams.multiplier`. The 1x base model lives in the `model_rate_settings` singleton (`baseModelId`); stored rates never change when the base switches — the base is a read-time divisor, so relative prices stay constant and the change is reversible. `/v1` billing (`lib/ai-relay.ts`), the model plaza (`lib/model-plaza.ts`), `/v1/models`, and the console all call `resolveModelRates`. models.dev metadata is cached in-process for 24h AND persisted to the `model_metadata` singleton after every successful fetch: a cold instance that cannot reach models.dev falls back to that snapshot instead of collapsing every model to 1x.
- Versioned entity mutations must remain in the MongoDB transaction that increments the user `syncVersion` and stamps the entity `version`; sync reads first capture the waterline and bound collection queries to it. The legacy merged `GET /api/sync` (no `collection=`) is bounded to `SYNC_MAX_LIMIT` per collection and reports `truncated` plus a delivered-only `latestVersion` — never return the user's full `syncVersion` for a truncated page, or the skipped rows are never pulled again. All four synced collections (`agents`, `conversations`, `providers`, `projects`) need a `{ userId: 1, version: 1 }` index. Upstream model ids are the reverse: `upstreams.models` is the single source of truth for what an upstream serves (`listUpstreamsForModel`'s query, the model plaza, `/v1/models`, and relay failover all read only it) — a per-model stop keeps the id in `disabledModels` while removing it from `models`, and deleting a model drops it from `models`, `disabledModels`, and `modelMeta` alike.
- Messages are embedded in conversations and models are embedded in providers. Deletes are soft deletes so tombstones remain available to `GET /api/sync?since=N`.
- Multimodal images are NOT stored as blobs: each message may carry a `partsJson` string (validated by `messageSchema`, stored verbatim, returned untouched by sync). Image parts embed the full base64 `data:` URI plus the sender's device-local path; clients rebuild missing local files from the `dataUri` after a pull. Do not strip, re-encode, or reorder `partsJson` server-side — the mobile client relies on byte-identical round-trips.
- Avatar objects are stored in a private S3-compatible bucket behind `lib/blob-store.ts`. `lib/avatars.ts` handles prefix snapshots/replacement/rollback, authenticated avatar GET routes stream content through ETag-conditional responses, and a recorded `avatarUrl` whose object is gone is a 404 (`fetchAvatarWithConditional` returns null), not a 500. `lib/avatar-locks.ts` serializes changes through MongoDB. Every avatar mutation path — user, agent, and market agent — MUST run inside `withAvatarLock` and thread the `verify` callback through snapshot/upload/revert/delete; unpublishing a market agent deletes its object. New modules must go through the `BlobStore` interface, never the SDK directly.
- All users (including admins) share the `messenger_session` JWT cookie from `lib/auth.ts`. `requireUserSession()` accepts any valid session; `requireAdminUser()` additionally verifies the database `role === "admin"` — every admin-only route and page must go through it. There is no separate admin cookie and no `ADMIN_PASSWORD` env.
- **Sessions are server-side** (`lib/sessions.ts`, `user_sessions` collection) and do double duty: (a) the JWT is only a credential and must carry `sid`; `requireUserSession()` rejects a token whose `sid` has no row, so logout / password change / the 30-day expiry take effect immediately (a plain JWT cannot be revoked); (b) each row is a **sync-progress ledger** — `syncCursor` records the `syncVersion` that session has fully applied. Signing in mints one row per device (several coexist, none displaces another); sign-out / password change / expiry DELETE the row (sessions carry no tombstones — a missing row is an invalid session) with the `expiresAt` TTL index as the backstop. `DELETE /api/auth/account` deletes the user's sessions. Tokens issued before this change have no `sid` and are rejected, so every client re-logs in once after upgrading.
- **Entity tombstones are purged from the session ledger** (`purgeSettledTombstones`): soft-deleted agents/conversations/providers/projects must stay until every client has pulled them, and nothing used to record that, so they accumulated forever. Now the account's OLDEST live session's `syncCursor` C is a safe lower bound — delete every tombstone with `version <= C`, since delta sync only ever asks for `version > since`. It runs when a session's cursor advances and at login. Two conservative rules: no live session ⇒ purge nothing (a re-logged-in device returns with its own local cursor and still needs them), and `syncCursor == 0` ⇒ purge nothing (that session's local state is unknown). Clients report the cursor through `GET /api/sync?ack=N`, which MUST be the version they have DURABLY applied — never the `since` of a post-push pull (that version is not applied yet), which is why the engine sends its stored cursor rather than echoing `since` and sends nothing on a full pull (`since=0`, local state being rebuilt); requests without `ack` simply do not advance the ledger. The purge horizon is the 30-day session lifetime: a client offline longer than that must re-login, and login always rebuilds the local store in full instead of resuming from a stale cursor.
- Runtime logging (`runtime_logs` collection, admin 系统日志 page at `/console/admin/logs`): `instrumentation.ts` installs a console capture in the Node runtime only (Edge returns early and delegates `onRequestError` to `instrumentation-node.ts`), wrapping `console.error/warn/log` to mirror every line into `runtime_logs` while still writing stderr/stdout. `instrumentation-node.ts` also exports `recordRequestError` for framework-level uncaught errors (carries `request.method/path` + route metadata). Business nodes log structured events through `createLogger(source)` from `lib/runtime-logs.ts` — `source` ∈ `api|relay|auth|billing|admin|sync|market|avatar|storage|migration`, and `details` holds the structured context. `runtime_logs` carries a 30-day TTL index; do not log successful per-request events (relay settlement, sync pages, login success already live in `usage_logs`/`auth` audit rows) — only errors and state changes, or the table becomes a heartbeat log and the admin page's `countDocuments`/`skip` pagination degrades. `recordRuntimeLog` is fire-and-forget and falls back to the raw (unwrapped) `console.error`, with a `capturing` re-entrancy guard in the wrapper. Add a `createLogger(<domain>)` call at new key nodes (success paths and expected failures) rather than instrumenting individual `console.error` sites. The page's table shows only time / level / source / summary; `method`, `path`, `status` and the raw `details` live in a per-row dialog (`components/admin/log-detail-table.tsx`), because those columns are `—` for every non-HTTP source. The RSC page formats both the timestamp and `details` (indented JSON) before handing rows to that client component — never send the raw `details` object across the boundary, and never format dates in the client (browser and server time zones differ, which would also break hydration).
- The first-admin invariant is enforced in two places: the registration transaction (unique `system_bootstrap` marker makes concurrent first registrations produce exactly one admin, retried as a plain user on marker conflict) and the idempotent `ensureAdminBootstrap` migration in `lib/mongo.ts` (promotes the earliest-registered user of pre-SaaS deployments).
- Billing and the AI relay are split across `lib/apikeys.ts` (key/card-code generation), `lib/quota.ts` (quota state, token estimation, `cost = max(1, ceil((promptTokens − cachedTokens) × inputRate + cachedTokens × cacheReadRate + completionTokens × outputRate))`; all three rates zero → free; usage_logs.promptTokens stores UNCACHED input only, cached read tokens are separate), `lib/ai-proxy.ts` (Bearer-key auth + OpenAI error bodies), `lib/ai-formats.ts` (the four wire formats — OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini Interactions — decoded into one IR and re-encoded, requests and SSE both ways; dependency-free so it can be exercised outside Next; the decoders own tool-call identity: consecutive sibling `function_call`/`function_result` items are one assistant turn with multiple calls, and a per-request ledger guarantees every call and its result resolve to the same id — synthetic when absent, unmatched results dropped, unanswered calls closed with an explicit error result), `lib/ai-relay.ts` + the four `/v1/*` routes (upstream failover by `priority`, upstream format chosen per upstream `apiFormat`; `auto` = follow the client's protocol AND relay it verbatim — the client's request bytes and the upstream's response/SSE bytes are forwarded untouched with no IR round trip, only a side-channel `data:` sniff for `usage`, so nothing is added or rewritten; configured formats still go through stream conversion with usage sniffing; post-completion quota settlement; every attempt — connect failure, 5xx, unparseable body, or a retryable 4xx — is recorded through `createLogger("relay")` and fails over, only 413/415 short-circuit, and an exhausted pool returns 502 naming each attempt). There is NO global model catalog: `/v1/models` serves the union of enabled upstreams' models, and per-model metadata resolves per model — `modelMeta[modelId].override` ON uses that entry's custom values, OFF uses live models.dev metadata (`lib/model-metadata.ts` — api.json only, 24h cache, input/output/cache-read rates normalized against `deepseek/deepseek-v4.1-flash`, `cache_read` missing falls back to the input price). Context windows are NOT served: clients derive them locally from models.dev `models.json`. Missing rates default to 1x (0 = free is only reachable via an explicit custom override). Card codes embed a creation-time plan snapshot so plans can be edited or deleted without invalidating outstanding cards.
- User-center routes: `PUT /api/auth/profile` (nickname only — avatars stay on the shared `/api/avatars/user` multipart endpoint so web and app hit the same blob/lock/rollback path) and two-step e-mail rebinding (`POST /api/auth/change-email` then `/confirm`). Rebinding requires the current password (the address *is* the login identity), sends a 6-digit code to the NEW address, and the code is bound to `(userId, email, code)` because a 10^6 space is guessable; consuming it marks the new address verified and revokes every other `auth_tokens` row for the user. Sessions survive the change — they key off the user id, not the address.
- Account routes include authenticated password changes at `PUT /api/auth/password` and permanent account deletion at `DELETE /api/auth/account`; deletion removes the user's MongoDB entities, billing history, usage logs, `user_quotas` entitlements, pending `auth_tokens`, avatar locks, and avatar blobs before clearing the session cookie. The last admin cannot delete or demote themselves (`409`): `ensureAdminBootstrap` never re-promotes once the `system_bootstrap` marker exists, so the instance would lose every management entry point permanently.
- The self user view is single-sourced in `lib/user-view.ts` (`buildSelfUserView`): `GET /api/auth/me`, `POST /api/auth/login`, `POST /api/auth/register`, `PUT /api/auth/profile` and `POST /api/auth/change-email/confirm` all return it, including `quotaBalance`/`quotaExpiresAt`/`quotaEntitlements`, `aiApiKey`, `displayName`, and `emailVerifiedAt`. Clients treat the login response as the account snapshot, so any field missing there reads as "0 quota / no builtin AI provider" until the next refresh — never add a self-facing field to `/me` only.
- **E-mail flows** are optional at the deployment level and split across `lib/env.ts` (`smtpSettings()`, `null` when `SMTP_HOST` is unset), `lib/mail.ts` (nodemailer transport cached on `globalThis`, delivery failures logged and swallowed), `lib/auth-mail.ts` (`prepareVerificationEmail` / `preparePasswordResetEmail` / `prepareEmailChangeCode` issue the token and return a delivery thunk), and `lib/auth-tokens.ts` (`auth_tokens` collection). Tokens are single-use and stored as SHA-256 digests keyed by `_id`, so `findOneAndDelete` is the atomic consume; re-issuing deletes the user+purpose siblings, and a TTL index on `expiresAt` is only the backstop. Registration issues the verification token inline but delivers through `after()`, so the 201 never waits on SMTP; `POST /api/auth/verify-email/resend` re-sends for a signed-in user. `POST /api/auth/forgot-password` returns the same `{ success: true }` for unknown addresses (no account enumeration) and `503` when SMTP is unconfigured — never fake a send. `POST /api/auth/reset-password` consumes the token before hashing, revokes every session of the account plus all remaining tokens, and marks the mailbox verified. Verification is informational: it gates no feature, only the reset mail and the console reminder.
- Agent Market entries live in a separate `market_agents` collection and contain only portable Agent snapshots (name, avatar, prompt, sampling parameters) — never providers, model bindings, or API keys. List/detail/publish/update/unpublish APIs require a Messenger session; market avatars stay private Blobs streamed through authenticated `/api/market/agents/{id}/avatar` routes. Imported Agents keep their market entry/version link but always clear model bindings; market updates require explicit user confirmation.
- Registration seeds the one required default Agent in the same transaction as user creation, so cloud data preserves the default-agent invariant. Default-role transfer is a claim: a `PUT` with `isDefault: true` demotes the incumbent inside the same `withVersionedWrite` transaction and stamps it with the new `version` (otherwise the demotion never enters the sync delta). A `PUT` that demotes the current default is deferred (the holder keeps the role) instead of rejected, because the client expresses a transfer as two PUTs in either order — rejecting either direction makes the role untransferable.

## Environment

- Copy `.env.example` to `.env.local`. `JWT_SECRET` and `MONGODB_URI` are required at runtime; `MONGODB_DB_NAME` defaults to `messenger`, and `APP_BASE_URL` defaults to `http://localhost:3000`.
- SMTP (optional): `SMTP_HOST` unset disables all outgoing mail (`mailEnabled()` is false) — registration still succeeds, accounts stay unverified, and `/forgot-password` answers `503`. When set, `SMTP_PORT` (default `587`), `SMTP_SECURE` (default: implicit TLS only on 465), `SMTP_USER`/`SMTP_PASSWORD` (optional), and `SMTP_FROM` (default: `Messenger Cloud <no-reply@APP_BASE_URL-hostname>`) configure the relay. nodemailer is a production `dependencies` entry and is pinned in `serverExternalPackages` in `next.config.ts`, so the Docker runner's prod-only `node_modules` must keep it resolvable.
- Avatar storage: `S3_BUCKET` is required; `S3_REGION` defaults to `us-east-1`; `S3_ENDPOINT` is optional. Supply `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` together or omit both to use the AWS credential chain. `S3_FORCE_PATH_STYLE=true` enables path-style addressing. Keep the bucket private and grant the server list/read/write/delete access.
- Keep secrets out of source control; `.env.*` is ignored except `.env.example`.
- Self-hosting: `Dockerfile` + `compose.yaml` package the server alone (MongoDB, S3-compatible storage and nginx are external). The runner stage gets production dependencies only, runs `next start` as the `node` user, and healthchecks `/api/plans`. Back up the bucket together with MongoDB. Any new runtime dependency must therefore be a `dependencies` entry, not `devDependencies`; keep `next.config.ts` free of options that break `next start` (for example `output: "standalone"`, which Next rejects at runtime).

## Conventions

- Use the `@/*` path alias for imports from the repository root.
- API handlers validate request bodies and route IDs with the Zod schemas in `lib/validation.ts`, authenticate before accessing user data, and map storage failures through `lib/route-errors.ts`.
- Keep API routes that touch MongoDB or Blob on the Node runtime (`export const runtime = "nodejs"`).
- Segment config exports (`runtime`, `maxDuration`, `dynamic`, `revalidate`, `fetchCache`, `preferredRegion`, `dynamicParams`) MUST be written inline as a literal in the route/page file, at most wrapped in `satisfies`. Next parses them statically without resolving imports, so `export const maxDuration = RELAY_MAX_DURATION_SECONDS` aborts `next build` with `Unknown identifier … at "maxDuration"` (exit 1) — the `/v1` relay routes pin the literal with `120 satisfies typeof RELAY_MAX_DURATION_SECONDS` so `pnpm typecheck` catches drift instead.
- Outbound URLs (upstream `baseUrl`, probe/test targets) MUST pass `assertOutboundUrl()` from `lib/outbound-url.ts` before any `fetch`: the relay attaches the stored upstream key to that URL, so an unchecked value is both SSRF and credential exfiltration. It rejects non-http(s) schemes, loopback/private/link-local/CGNAT/ULA/multicast/reserved ranges (including `::ffff:` IPv4-mapped forms) after DNS resolution.
- Secret-guessing endpoints (login, register, card preview, redeem) MUST consume `consumeRateLimit()`/`enforceRateLimits()` from `lib/rate-limit.ts`; the counters live in MongoDB so they survive serverless horizontal scaling. Preview and redeem share one bucket so preview cannot be used as an unmetered card-code oracle.
- **Embedded web Messenger**: `/console/messenger` is the authenticated browser chat surface. It hydrates from the existing sync collections, persists conversations through `/api/conversations/:id`, and sends AI requests through the same-origin `/api/chat` proxy. `/api/chat` must keep the user's built-in AI key server-side and delegate to `relayCompletion`; do not expose the key to browser storage or add a second relay implementation.
- **Web configuration management**: `/console/manage` is the authenticated CRUD surface for Agents, Providers, and Projects. It must use the existing `/api/agents/:id`, `/api/providers/:id`, and `/api/projects/:id` versioned mutation routes so web edits remain in the same sync stream as mobile and desktop edits.
- Agent role management keeps `role: "title"` single-owned like the clients: claiming the title role demotes the previous holder to `chat`; the default Agent remains a separate invariant and cannot be a title Agent. The Web editor presents default/chat/title as roles, hides follow-default controls for the default role, and allows title Agents to follow the default Agent. Agent model forms use a provider-first/model-second picker and include built-in `Messenger Cloud AI` (`builtin-messenger-cloud-ai`) models from the model plaza.
- **Web Messenger rendering**: `/console/messenger` renders message Markdown with `markdown-it`, math with KaTeX, `<think>` sections as collapsible thinking blocks, and `partsJson` tool calls/results as tool cards. Consecutive assistant/tool messages are merged into one Agent turn before rendering, drawn as a single bubble with one avatar whose thinking/tool cards span the full bubble width: text and `<think>` reasoning are merged in order, and each `tool_call` is paired with its `tool_result` (by `callId`) into a single collapsible card that is collapsed by default; tool-role content is never rendered as a normal bubble. Message rows must remain `min-width: 0` with horizontal overflow contained inside code/table blocks; user and Agent avatars use the authenticated avatar endpoints. The UI is built only from shadcn components (`ScrollArea`, `Collapsible` for thinking blocks, `Empty`, `AlertDialog` for delete confirmation) and theme tokens (`bg-background`, `bg-muted`, `bg-sidebar`, `text-muted-foreground`, …) so it follows the system light/dark theme like the rest of the console — never hardcode palette colors (`slate`/`cyan`/hex) in `messenger-app.tsx` or the `.markdown-body` rules in `app/globals.css`. `ScrollArea` instances that hold truncating content need `[&_[data-slot=scroll-area-viewport]>div]:!block`, otherwise Radix's `display: table` wrapper stops `truncate`/`min-w-0` from working.
- **Web projects**: `/console/messenger` lists synced projects as folders (entering one shows only its `projectId` conversations; new chats created inside inherit it). The web cannot create or edit projects — they come from the other clients. The tab registers itself as a relay device (`components/messenger/remote.ts`, one `web-<uuid>` id per tab in `sessionStorage`) and a project is usable only while its `deviceId` owner is in the `presence` set; otherwise (no owner / owner offline / relay down) the composer is disabled but history stays readable. The tool loop lives in `sendMessage`: the model request, persistence and SSE stay in the browser, and only a workspace tool call crosses devices via `POST /api/remote/tool-call` → `toolResult` event (10-minute timeout, abort/offline settle the call as an `isError` result and send `tool-cancel`). Tool declarations and the enable/read-only rules in `components/messenger/chat-wire.ts` mirror `core/rust/crates/messenger-tools` (conversation override → Agent, following the default Agent when `toolsFollowDefault`; `edit`/`create` only when the conversation is writable) — keep them in sync. Stored history is sent back through `toWireMessages`, which drops unpaired tool calls/results, `<think>` text and failed replies. The Agent editor in `/console/manage` must keep the stored `toolsEnabled`/`toolsFollowDefault`/`toolsConfig` when saving (it has no tool controls).
- Every "new conversation" entry point in `/console/messenger` opens a shadcn `DropdownMenu` (`NewConversationMenu`) listing the chat Agents with avatar + name; the title-role Agent is excluded and the chosen Agent becomes the conversation's `agentId`.
- `/console/manage` uses shadcn `Tabs`, `Checkbox` and `AlertDialog` (no native checkboxes or `window.confirm`); page titles follow the console convention `text-xl font-semibold tracking-tight`.

- **Remote projects relay** (`lib/remote-hub.ts`, `lib/remote-relay.ts`, `/api/remote/*`): a project's `deviceId` names the device that owns its workspace; the relay lets the other devices of the same account run that project's workspace tools there. Each device holds one SSE connection (`GET /api/remote/events?deviceId=`) — connected means online — and `POST tool-call|tool-result|tool-cancel` forward payloads verbatim to `targetDeviceId`'s connection (`409` = target offline). Nothing is persisted. The online set lives in process memory on `globalThis`, so deployment MUST stay single-instance until it is swapped for a cross-process pub/sub (e.g. MongoDB change stream); every lookup is keyed by the session's `sub`, never trust a userId from the body. Long-lived connections re-check their session every 4th heartbeat and `deleteUserSessions` without `exceptSid` closes them at once, so revocation never waits for a natural disconnect. `projectSchema` is `.strict()`, so a new project field must be added to `lib/validation.ts` AND `lib/storage.ts::upsertProject` — and `upsertProject` deliberately keeps the stored `deviceId` when a legacy client omits it. The Rust core (`core/rust/crates/messenger-remote`) is the client; its contract is mirrored in `API.md` and `core/rust/crates/messenger-http/docs/REMOTE.md`.
